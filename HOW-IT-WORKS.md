# How NegPiP for Krea 2 and MOSS-Image works

Implementation notes for anyone reading or modifying the code. Nothing here is needed to use the extension — see the [README](README.md) for that.

Most of this document was written while Krea 2 was the only model and reads that way; the mechanism is the same on MOSS-Image, and [the MOSS-Image section](#moss-image) lists exactly what differs. The code is split along that line: `text.py` and `dit.py` hold the levers and the hooking and know no model, and one `ModelAdapter` per model (`krea2.py`, `moss.py`, interface in `adapters.py`) answers the questions they ask — which engine, which template, whether it is stripped from the conditioning, where the text sits in the joint sequence, which linear carries the values, how a mask reaches the attention.

Ported from [blue-pen5805/ComfyUI-krea2-negpip](https://github.com/blue-pen5805/ComfyUI-krea2-negpip), itself a Krea 2 adaptation of [hako-mikan](https://github.com/hako-mikan/sd-webui-negpip)'s original NegPiP.

## Relationship to upstream

This repository is a fork that keeps the *idea* and none of the code: the ComfyUI node was removed when the port landed, so there is nothing here for an upstream merge to touch. Two things follow from that, and both are worth re-checking rather than assuming.

Upstream's ComfyUI-side compatibility fixes generally do not have counterparts here, because the framework underneath is different. `ref_latents` becoming a positional argument on ComfyUI's diffusion-model wrapper is one: Forge Neo's `SingleStreamDiT.forward` reads reference latents from `dynamic_args.ref_latents` instead, and `dit.py` calls every wrapped forward by keyword past the required positionals specifically so that class of change cannot silently reroute an argument. Batching several token rows into one `clip.encode` call is another: Forge's engine encodes one chunk at a time.

The *hazards* those fixes describe are worth reading even when the fix itself does not port. The row-batching one is really about a non-integer token expanding into several sequence positions, which would leave the per-token rows indexing the wrong tokens — `_encode_line` guards that with its `aligned` check, and stands the prompt down rather than misplacing a sign flip.

## Why the existing Forge port does not cover Krea 2

[sd-forge-negpip](https://github.com/Haoming02/sd-forge-negpip) has three paths, and Krea 2 fits none of them. SD1 and SDXL encode the negative fragment separately, append it to the cross-attention context, and negate the tail of `to_v`. Anima rides a mask through its dedicated `SelfCrossAttention` module. Krea 2 has no cross-attention at all: it is single-stream, so the text tokens sit in the *same* self-attention sequence as the image patches (`backend/nn/krea.py`, `SingleStreamDiT.forward` concatenates them). And its conditioning is not an embedding — it is a 12-layer × 2560-feature Qwen3-VL tap stack that goes through a two-stage text-fusion transformer before any attention sees it.

## The two halves

**Weights out of band.** Forge's emphasis pass multiplies the encoder's hidden states by the prompt weight, so a negative weight arrives as a sign-flipped *hidden state*. On SD1/SDXL that is close enough — the conditioning feeds `to_k`/`to_v` directly, both linear. On Krea 2 the RMSNorm and SwiGLU of the text-fusion stack are not odd functions, so a negated tap stack is simply a *different prompt*, not an inverted one; and RMSNorm being scale-invariant, a *scaled* one is barely scaled at all. So a claimed weight is taken away from the emphasis pass — which sees a flat `1.0` for those segments — and travels alongside the conditioning as two per-token rows: a **value factor** and a **logit bias**.

The ComfyUI node smuggles the same information through a sidecar token appended to the conditioning tensor, with magic constants and a checksum, because ComfyUI's graph gives it no other channel. Forge does have one: extra `model_conds` entries ride through `reconstruct_cond_batch` → `compile_conditions` → `apply_model` and land as keyword arguments on the diffusion model, batched and repeated in lockstep with the conditioning they describe. So the sidecar is gone, and with it every way it could be mangled — and because each row travels *with* its own conditioning, the positive and negative prompts cannot read each other's, which is what lets weights work in both at any CFG.

**Act inside attention.** Both rows are applied in the DiT, after text fusion has run, over the text positions of the joint sequence — the leading `txtlen` on Krea 2, whose DiT concatenates `cat(text, image)`, the trailing `txtlen` on MOSS-Image, whose DiT concatenates `cat(image, text)`.

The value factor scales the output of each selected block's `wv`: attention still scores the token normally, then subtracts, damps or amplifies what it contributes instead of adding it as-is. A token's share of the attention output is linear in this factor, so it works above `1.0` as well and never saturates, and it needs no mask, so it runs on every attention backend. The logit bias is added to the token's attention score, multiplying its softmax weight by `exp(bias)` for every query in the sequence. That is a different kind of emphasis: it changes how much the sequence *attends* to the word rather than what the word contributes, the other keys lose the share the flagged one gains, and it saturates as that share approaches one. An earlier version of this document had the two the wrong way round, claiming the value lever saturates; it is the bias that does. Inside attention, that is. In the finished image the order reverses: on a fixed seed, values at `1.5`, `2` and `3` give 35%, 39% and 42% blue-dominant pixels where the bias at gain `1.0` gives 36%, 43% and 71%, because what one word contributes is a small part of each block's output and every block normalises again, while a larger share of the attention compounds over the blocks. That measurement is why the attention lever is the default for weights above `1`. Both levers can take `w > 1`, chosen by *Amplify emphasis in values* and *Handle emphasis in attention*; the value-side one is the one [flyfront/sd-forge-negpip](https://github.com/flyfront/sd-forge-negpip) calls V-Scaling, with a linear `1 + strength*(w-1)` here in place of their `|w|^strength` so it is the negative side's formula continued upwards.

Two hooks do it: the module nearest the attention that receives `transformer_options` gets its `forward` wrapped, to park the value factors for the duration of one call and to get the bias into the attention the way the model allows — on Krea 2 that is the `Attention` module, and the bias is substituted for its `mask` argument (Krea 2 never passes one — the DiT hands `None` to every block); and the linear that produces the values gets a wrapper that scales the rows the parked factors name — Krea 2's `wv`. Nothing of Forge's own attention math is copied, so an upstream change to Krea 2's attention does not silently break either lever. The bias does need a backend that accepts an additive mask, so `krea.attention_function` is pointed at the plain SDPA path while one is in play, and put back afterwards. The MOSS-Image counterparts of each of these are in [its section](#moss-image).

`txtfusion.layerwise_blocks` are deliberately left alone: they run at `(batch * seq, taps, dim)`, so their sequence axis is the 12-layer tap stack, and the rows do not index it.

## Why the flip is about the prompt mean and not about zero

`v -> -v` is the whole of NegPiP everywhere else, and it carries a term that has nothing to do with the word being flipped.

Attention output is a *convex* combination of value vectors, `sum_j a_j v_j` with the `a` summing to one, and the text tokens' values share a large common component — write `v = vbar + d`. Scaling one token by `m` perturbs every query's output by `a_t (m-1) v_t`, which at `m = -1` is `-2 a_t (vbar + d)`. The `d` part is the word. The `vbar` part is not: it is the same vector subtracted from every query in the sequence, so it lands in the residual stream as a shared offset, and the next block's `RMSNorm` divides by a norm that offset has grown — shrinking the token-to-token variation around it, which is spatial detail. It happens at all 28 blocks, and, this being single-stream, to the text tokens as well as the image patches, so the prompt's own representation carries it forward too.

`_apply_value_flip` therefore scales about `vbar` instead: `v -> vbar + m (v - vbar)`, so the perturbation is `a_t (m-1) d` and its shared component is exactly zero. `vbar` is the mean over the tokens the row leaves alone, recomputed per block from that block's own `wv` output. The suppression is untouched — `d` is inverted just as hard. The slider interpolates between the two, `0.0` being the original behaviour.

Cross-attention models are not exposed to this the same way: there the flip lands in a side branch whose only queries are image patches, and the original NegPiP appends a *separately encoded* copy of the fragment rather than negating a token already in the sequence.

**On magnitude.** The `-2 vbar` term is exact and easy to confirm in isolation — feed `_apply_value_flip` synthetic anisotropic values and the shared component of the change is `-1.997` at `reference = 0.0` and `+0.002` at `1.0`. What it is worth in a finished image took a while to pin down, because it is second-order and the split-encode dilution above swamps it: compared with single-pass off, where everything above a fifth of Nyquist sits at 24-35% of a no-weight baseline, the two references are indistinguishable. With single-pass on and the dominant term gone, one seed separates them cleanly — `reference = 0.0` leaves a hole across six consecutive mid bands, 0.35-0.74 of baseline against 0.82-0.94 at `1.0`, and mean gradient at 80% of baseline against 96%. The shape fits the mechanism: a shared offset compresses variation in the residual stream, which is broad regional contrast, so the *mid* bands go while fine texture injected late survives (0.87-0.97 at the top). That is a different signature from the dilution damage, which is worst at the top. One seed, so treat the size as provisional; the sign and the shape are not in doubt.

## Getting the weights onto the right tokens

**`compile_conditions` learns a third shape.** It knows a bare tensor, or a dict with both `crossattn` and a pooled `vector`. NegPiP conditioning is `crossattn` plus the rows and no pooled vector, which would have raised `KeyError: 'vector'`. The rows are registered as `ConditionCrossAttn`, the class the conditioning itself uses: when cond and uncond differ in token count Forge batches them into one forward pass by repeating the shorter along the token axis up to the lcm (when the multiple is at most 4), and a plain `Condition` refuses to concat on any shape difference, which ran cond and uncond as two passes whenever NegPiP was on and the counts differed. Tiled by the same rule the rows stay 1:1 with the tiled tokens by construction; an earlier version registered them as plain `Condition`s out of the opposite worry. The wrapper is installed on demand, is a straight pass-through for every other shape, and is never removed — Forge caches compiled conditioning on the `StableDiffusionProcessing` *class*, so a cond can outlive the run that made it.

**The rows cover the words, not the boilerplate.** The split encode wraps *every* weighted segment in the full chat template, so a prompt carrying weights tokenises to several copies of the template with the fragments spliced between them. Emphasis scales all of it, which was Forge's own behaviour until `21886f41` and is what an unclaimed weight still gets — but flipping the sign of the system instruction is not what `(word:-1.0)` asks for. Both rows are confined to the fragment itself, located structurally inside each templated segment rather than at an assumed offset.

How much boilerplate that is, is easy to underestimate. The template strip counts `<|im_start|>` occurrences and stops after two, so it removes the system instruction from the *first* segment only; every later segment keeps its copy of `<|im_start|>system\nDescribe the image by detailing the color, shape, ...:<|im_end|>` intact inside the conditioning. `a portrait of a woman posing on a beach. high quality analog photo, highly detailed.\n(watermark:-1)\n` parses to three segments and encodes as 734 characters against the unweighted prompt's 307, most of the addition being that instruction twice more. The words that were doing the work end up with roughly a quarter of the attention mass they had — which is where the softening people notice actually comes from, ahead of the value flip by a wide margin. It was Forge's own behaviour for any weighted Krea 2 prompt until `21886f41`, extension or no extension, which is why *Encode the prompt in one pass* now defaults on.

Measured on Krea 2's own tokenizer, `a portrait of a woman posing on a beach. high quality analog photo, highly detailed.` plus `(watermark:-1)` encodes to 103 conditioning tokens against the unweighted prompt's 23 — 80 of them two verbatim copies of the system instruction — and one-pass brings that to 25. The images agree: against a no-weight baseline at a fixed seed, the split encoding keeps 24-35% of the power above a fifth of Nyquist, and one-pass keeps 89-101%. Mean gradient goes 68% -> 96% of baseline, Laplacian RMS 58% -> 96%. Whatever else a negative weight does to an image, this was nearly all of the softening.

**Or the extra templates never happen at all.** *Encode the prompt in one pass* rejoins the parser's segments and encodes that once, locating each fragment by character offset and assigning every token to whichever segment covers most of its characters — so a BPE merge across a segment seam lands in exactly one of them. Characters that are not whitespace count first: Qwen's BPE carries the space *before* a word inside the word's token, so in `, (a red apple:-1.0)` the token ` a` has its space in the unweighted segment and its letter in the weighted one, and by plain character count the one-letter word was a tie, which went to the earlier segment and left `a` unflagged (`NegPiP Enable (Positive: 2)` for a three-word phrase). Whatever is still tied goes to the earlier segment. The token stream is the templated prompt as the engine's own tokenizer encodes it; the offsets only have to agree with it, and are checked against it before being used.

**When neither offset source works, the segments are tokenised separately inside one template.** `_tokenize_joined` splits `llama_template` at its placeholder, tokenises the prefix, each parsed segment and the suffix as separate strings, and concatenates the id lists, so every segment's tokens are its own by construction and the rows need no localisation at all. This is [flyfront/sd-forge-negpip](https://github.com/flyfront/sd-forge-negpip)'s one-pass method, and it is their only one. What it gives up against the exact path is byte-identity with the unweighted prompt: a BPE merge that would have crossed a segment seam cannot happen, so a token or two can differ at a seam. One seam effect is avoided on purpose, after flyfront's later fix: the parser leaves a segment's trailing space with that segment (`a cat, ` / `red` / ` hat`), and a segment tokenised on its own would then lose the leading-space merge the word has inside the sentence (`Ġred`), so the trailing whitespace of each segment is moved to the start of the next before tokenising. With that, `a cat, (red:-1.0) hat` tokenises to the same ids as `a cat, red hat` on both models' tokenizers, and the flagged token is the space-carrying word. The template appears once and the sentence is otherwise the sentence, which is what matters; the split encode, which repeats the system instruction per segment, is now only used when one-pass encoding is switched off, on Krea 2. The log says which of the two one-pass paths produced the stream, once per session.

**Where the offsets come from matters more than it looks.** The obvious source is the tokenizer, and an HF *fast* tokenizer reports them directly — but Krea 2 does not have one. The checkpoint ships `vocab.json` and `merges.txt` with no `tokenizer.json`, `model_index.json` names `Qwen2Tokenizer`, and `backend/loader.py` instantiates that class by name, so on the `transformers==4.57.6` Forge Neo pins it is the slow pure-Python tokenizer, which raises `NotImplementedError` on `return_offsets_mapping`. For as long as that was the only source, single-pass encoding stood down on *every* Krea 2 prompt — while `Krea2 NegPiP single pass: True` went on appearing in the infotext, so toggling it produced bit-identical images and read as "this option does nothing". Exactly the silent stand-down this port already lost time to once. `_decoded_offsets` is the second source: the span of token `i` is what decoding one more token adds to the decoded prefix. That is not a guess about where a fragment landed — the whole result is discarded unless decoding the full stream reproduces the templated prompt character for character, and it reproduces a fast tokenizer's own offsets exactly on Latin, accented, CJK, emoji and Cyrillic prompts. Only if both sources fail does it fall back to the joined path above, and it says so in the log when it does.

This is what makes the conditioning for `a portrait (blurry:-1.0) sharp` byte-identical to `a portrait blurry sharp` — and it only holds because a claimed weight already leaves a flat `1.0` behind in the emphasis multipliers.

## MOSS-Image

MOSS-Image reaches Forge Neo two ways, and the adapter handles both. Forge's own support landed in `be6fa5d4` (2026-10-21): `backend/diffusion_engine/moss_image.py`, `backend/text_processing/moss_image_engine.py` and `backend/nn/moss_image.py`. Before it, the third-party [eduardoabreu81/moss-image-forge-neo](https://github.com/eduardoabreu81/moss-image-forge-neo) extension (0.1.x) registered its own engine (`MossImageEngine`), text engine (`MossTextEngine`) and DiT (`MossImageDiT`); it hooks Forge's loader ahead of the built-in detection, so while it is installed its engine is the one that loads. The model is the same and so is everything the hooks need, and what differs is plumbing, so `moss.py` is one `MossAdapter` base with `MossNativeAdapter` and `MossExtensionAdapter` on it. Everything below was read in those sources and cross-checked against flyfront's `neo` branch, which got to both backends first. Nothing is imported from the extension by path: the adapter resolves the engine from `shared.sd_model` and its module through `sys.modules[type(engine).__module__]`.

**Detection.** Native: `type(model).__name__ == "MOSSImage"` with a `text_processing_engine_qwen` — the attribute Krea 2's engine uses too, and `detect` tries Krea 2 first by its own name. Extension: `"MossImageEngine"` or `model.is_moss_image`, text engine at `model.text_engine_moss`. `engine_problem()` checks what each flavour touches before anything is patched: the native engine's `llama_template`, `tokenizer.tokenize_with_weights` and `text_encoder.encode_token_weights`; the extension's `TEMPLATE`, `MAX_LENGTH`, `token_ids` and `encode`. The DiT is duck-typed on what the hooks touch: 42 `layers` of width 3072 (`dim` on the extension's DiT; Forge's keeps no such attribute, so the width is read off `video_embedder.out_features`), each with a `proj` `ModuleDict` carrying `qkv` or `v`, `text_embedder.blocks` each with a `qkv`, and the attention callable the flavour swaps. A miss stands the extension down with a line naming it.

**The template is not stripped.** Both engines return `(T, 4096)` per line, no batch axis, for the *whole* templated prompt (`<|im_start|>user\n{}<|im_end|>\n<|im_start|>assistant\n<think>\n`; the extension truncates at 4096 tokens, Forge does not); the DiT reads every token, template included. So `template_end` is `0`, the rows cover the whole sequence, and the template tokens carry a neutral `1.0` / `0.0`. The rows are `(T, 1)`, 1:1 with that leading axis; Forge's batching stacks them to `(B, T, 1)` next to the `(B, T, 4096)` conditioning, and the DiT hook reshapes either model's rows to `(B, T, 1)`.

**The token ids are the engine's own.** `Qwen359BEngine.__call__` strips the line (an empty one becomes a single space), wraps it in the template unless it already starts with `<|im_start|>`, and tokenises through `SDTokenizer.tokenize_with_weights(..., disable_weights=True)`, which unescapes `\(` and `\)` first and otherwise hands the whole string to the Hugging Face tokenizer. `MossNativeAdapter.plain_ids` makes that very call, so an unweighted line's stream is the engine's to the token, and a line of raw chat markup is verbatim. The native tokenizer is instantiated by `model_index.json`'s class name, `Qwen2Tokenizer`, which on the `transformers` Forge pins is the slow one, as for Krea 2, so `return_offsets_mapping` raises and `_tokenize_single` takes its decoded-offsets branch; the extension ships `tokenizer.json`, is a `Qwen2TokenizerFast`, and gets the reported-offsets branch. The native check runs one weighted prompt through both branches and asserts identical streams and rows. The extension's `token_ids` strips, rebuilds a layout, templates and truncates, and `MossExtensionAdapter.plain_ids` is that call.

**What the engines do with weights: nothing.** Both hard-wire `EmphasisNone` and pass the prompt verbatim, brackets and all, so any weight needs this extension's encode. A claimed weight leaves `1.0` behind as on Krea 2, and the stream is then the unweighted sentence's own, so `(a red apple:-1.0)` encodes to exactly the engine's encode of the sentence without the weight. An unclaimed weight is applied through `text_encoder.encode_token_weights` with the multipliers as token weights, which is ComfyUI's output lerp — each weighted token's hidden state moved between the empty (pad) encoding and its own — and is what a ComfyUI user of the model gets; neither engine has an embedding-side pass for Forge's emphasis classes to be restored into, so *Original* and *No norm* both mean that lerp, and *None* and *Ignore* mean no weight. A prompt with no effective weight goes through the engine's own ids and encode, so it is byte-identical to the engine on its own.

**Layout prompts never meet the parser.** A MOSS-Image layout is one JSON object with `bbox` arrays `[y, x, y, x]`, and square brackets are de-emphasis to `parse_prompt_attention`. `split_verbatim` finds the object with `json.JSONDecoder.raw_decode` after the engine's own normalisation — the extension's `restore_layout_json` for a layout sd-dynamic-prompts has stripped the braces from, the native engine's `\(` / `\)` unescape — and hands it back as one neutral segment; **what follows the object is prompt**. That matters since `be6fa5d4`: Forge's built-in JSON Builder escapes every parenthesis in the layout (`\(`, which is not a JSON escape, so the unescape has to come first) and appends its *Extra* field after the object on a new line, so a builder prompt is `layout\nextra`, and the extra line can carry weights. `prompts.segments` is where the prefix goes in front of the parsed rest, and `scan` counts weights through it, so a layout alone never activates the extension and a builder prompt with a weight in *Extra* does. Weights inside a caption are not parsed; the builder escapes them to literal text anyway. The `BREAK` sentinel is neutralised as on Krea 2.

**Where the text is.** Both DiTs run the prompt through a projection and two text-only `TextBlock` refiners (`text_embedder.blocks`), then concatenate `cat(video, text)` — text **last** — and run 42 `Block`s over the joint sequence. So the rows map to the trailing `txtlen` positions, not the leading ones as on Krea 2; `_apply_value_flip` and `attention_bias` take the adapter's `text_first` and slice accordingly. In the refiners the sequence is the text alone and either slice is the whole of it.

**Where the values are.** `Block.proj` is a `ModuleDict` on both: Comfy-Org's files fuse q, k and v into `proj["qkv"]`, whose output `chunk(3, -1)` hands to `q, k, v` in that order, so the values are the last third of the output columns; upstream's diffusers export keeps a separate `proj["v"]`. The `TextBlock` refiners always have a fused `qkv` (a plain `nn.Linear` with bias). The adapter hands `dit.py` an `AttentionSite` per block with the linear and the column slice, and the value wrapper scales the flagged rows *inside that slice*, in place through a view, so q and k are not touched and nothing of either `Block.forward` is re-implemented.

**How the bias gets in.** Both DiTs' attention is a module-level function with no mask argument that ends in a callable looked up by name at call time, and that last call is the swap point. The extension's `transformer.attention(q, k, v, rope, heads, transformer_options)` rotates q and k, splits the heads and ends in `kernels.attention(q, k, v, transformer_options=...)` with the heads at `(B, H, S, D)`. Forge's `attention(q, k, v, q_norm, k_norm, pe, heads, transformer_options)` norms and rotates q and k and ends in `attention_function(q, k, v, heads, transformer_options=...)` with the heads still flat, `(B, S, H*D)`; the name is bound in `backend/nn/moss_image.py` at import, exactly as `krea.attention_function` is. Each flavour's `force_pytorch_attention` rebinds its callable to a wrapper that reads the bias out of `transformer_options`, pads it to the `[image, text]` key order and calls `backend.attention.attention_pytorch` with it, in the head layout it was handed, and passes a call that carries no bias to the original untouched. The hooked `Block.forward` and `TextBlock.forward` wrappers put the bias into a *copy* of `transformer_options` under a key of their own (`LIVE_BIAS_KEY`), so an unselected block, which sees the DiT-level key too, is not biased. The swap is installed only while a prompt asks for amplification, as on Krea 2.

**Signatures.** Native: `MOSSImage.forward(x, timestep, context, transformer_options={}, **kwargs)`, which copies `transformer_options` and so must be given a dict; `Block.forward(x, mod, pe, transformer_options={}, ref=None, ref_kv=None, kv_out=None)` since `c6c2b43d` (MOSS-Image Edit; four parameters before it) and `TextBlock.forward(x, pe, transformer_options={})`, called positionally by the DiT, by Skip Layer Guidance's block wrapper and by `preprocess_refs`. Extension: `MossImageDiT.forward(x, timestep, context, transformer_options=None, **kwargs)`, `Block.forward(x, rope, mod, dtype, transformer_options=None)` and `TextBlock.forward(x, rope, dtype, transformer_options=None)`. Forge calls the model with `context`, `control` and `transformer_options` by keyword, so the one DiT wrapper in `dit.py` takes `(x, timesteps, context, *args, transformer_options=None, **kwargs)`, pops the two row keys out of `kwargs` and passes the rest through, for every model. The block wrappers spell no parameter list out any more: `CallSignature` reads the wrapped method's signature once, and the wrapper takes `(*args, **kwargs)`, finds `transformer_options` (and on Krea 2 `mask`) by name wherever the caller put it, substitutes there and passes everything else through untouched. The version that spelled `(x, mod, pe, transformer_options={})` out raised `TypeError: Block.forward() takes from 3 to 4 positional arguments but 6 were given` the day the block grew its reference parameters.

**Edit.** `c6c2b43d` added reference images to MOSS-Image (Settings → *[Moss-Image] Reference Method*, `ai-toolkit` or `Moss-Image-Edit`). The engine mirrors Krea 2's bookkeeping: on a positive encode it consumes `ini_latent`, and with references and a method set it takes `get_learned_conditioning_with_image`, which encodes the reference latents, sets `dynamic_args.ref_latents`, `moss_reference_method` and `moss_ref_kv`, and for `ai-toolkit` puts vision placeholders into the token stream; on the plain branch it clears that state. `MossNativeAdapter.hand_back` hands the positive prompt back on the reference branch, as `Krea2Adapter` does, with one warning, and `before_encode` does the clearing on the plain branch so a stale reference cannot put the DiT into edit mode; the negative prompt keeps its rows. In the DiT both UI methods are *isolated*: the sequence stays `[image, text]`, and each block's attention appends the reference images' cached keys and values after the sequence's own (`preprocess_refs` runs the blocks over the reference tokens once, with an empty `transformer_options`, so the hooks are inert there). The value wrapper sits on the projection, before that concatenation, so the trailing-text rows are still the text; the bias is confined to the first `q.shape[1]` keys (`attention_bias(..., within=)`), where the text is, and is zero on the reference keys. The native check drives all of it against the real `MOSSImage` with a reference latent, and also runs on a Forge from before the commit, where the Edit checks report themselves absent.

**Guidance.** Forge's Skip Layer Guidance (`modules/processing_scripts/slg.py`, on by default for MOSS-Image, block 22) runs the uncond pass with the block replaced through `patches_replace`, whose wrapper calls the block positionally; the hooked block is still the block, so the skip skips it, hooks and all, and the native check asserts the hooked and unhooked skipped outputs are equal. The extension did the same with a `torch.where` per sample around the still-called block. The extension also patches `ConditionCrossAttn.can_concat` to refuse unequal lengths, so cond and uncond may arrive as separate batches there, as they do on native when SLG splits them; `_align_batch` handles a row batch that divides the call's batch.

**What is not done.** flyfront's query split (image queries read magnitude-scaled values, text queries sign-only ones) is not taken, for the reason given above; nor is their parsing of weights inside layout captions. No MOSS-Image images have been made by the author of this port; the README lists the first two prompts to try.

## Model detection

Each adapter answers `dit_problem(dit)` with `None` or a reason, and the script logs the reason once (`NegPiP stands down on <model>: ...`) before standing down. Krea 2's `is_krea2_dit` duck-types on the identifying constants (`txtlayers`, `txtdim`) and on the attributes the hooks actually wrap (`blocks`, `txtfusion.refiner_blocks`, `txtmlp`) — and on nothing else. Every attribute in that check is a thing the framework may move, so one that is not load-bearing is pure liability. This is not hypothetical: an earlier version also tested for `SingleStreamDiT._unpack_context`, purely because it looked distinctive. Forge moved that method into the text encoder, detection failed, and the extension stood down **silently** — no error, no log line, the UI intact, and images pixel-identical to having it switched off. Standing down is indistinguishable from a prompt with no weights in it, which makes it this extension's worst failure mode by a distance.

## Other Krea 2 NegPiP implementations

Two others exist for Forge Neo, and both were read when the value-side emphasis and the joined fallback were added; flyfront's was read again for MOSS-Image.

[flyfront/sd-forge-negpip](https://github.com/flyfront/sd-forge-negpip) is Haoming02's extension with a Krea 2 path ported from the same ComfyUI node as this one. It keeps the node's encoder-side lerp toward an all-pad encoding for magnitudes (dropped here on purpose; their own README calls it subtle, and their V-Scaling fades it out), applies `sign(w)·|w|^strength` to the value vectors of every weighted token, and runs attention twice per block so that only the image queries read the magnitude-scaled values while the text queries read sign-only ones. That last idea costs a copy of Forge's attention forward, which this extension avoids; for the logit bias the same restriction would be cheap, since `attention_pytorch` accepts a `(B, queries, keys)` mask. They do not neutralise the parser's `BREAK` sentinel, and they hook the 28 blocks only. Their `neo-moss` branch (2026-10-18) added MOSS-Image through the extension, and their `neo` branch (2026-10-21) Forge's own support beside it, auto-detected, which is where the facts in [the MOSS-Image section](#moss-image) were first established; it re-implements the extension's `Block.forward` wholesale to reach the values, where this extension wraps the fused projection and the kernel call instead, and it moves a segment's trailing whitespace into the next segment before tokenising, which `_tokenize_joined` now does too.

[hako-mikan/sd-webui-negpip](https://github.com/hako-mikan/sd-webui-negpip) added Krea 2 on 2026-09-04 with the original NegPiP shape: the negative fragment is removed from the prompt, encoded separately at weight 1, appended to the conditioning, and its value rows are multiplied by the weight in the 28 blocks and the refiners, through a wrapper on `wv` like the one here. Its README states that on Krea 2 only the sign of the weight has an effect, on the argument that each block's RMSNorm removes the scale. The block is pre-norm with an unnormalised residual, so that is not structurally forced, and on this implementation it does not hold: `(watermark:-0.5)`, `-1` and `-2` on one seed give three progressively different images (mean absolute pixel difference 12, 11 and 17 between the pairs), shown in the README. Their design appends the fragment as extra tokens rather than flipping it in place, so the two results are not in contradiction; the claim is about their path, not the model.

## Testing

Everything is verified offline against Forge Neo's real sources, with no GPU, no checkpoint and no running webui. Three scripts in `tests/`, run with Forge Neo's own interpreter (`venv/Scripts/python.exe tests/check_krea2.py`; they find Forge when the extension lives in its `extensions/` folder, else through `FORGE_NEO`), cover the Krea 2 path, the MOSS-Image path on Forge's own support (`check_moss_native.py`) and on the extension (`check_moss.py`, which needs the `moss-image-forge-neo` extension installed); the MOSS-Image ones also need a fast Qwen tokenizer (`QWEN_FAST_TOKENIZER`, or Qwen3-VL-4B's in the Hugging Face cache — the same `Qwen2TokenizerFast` class and BPE as the Qwen3.5 file the checkpoint ships, which is what matters for offsets and leading-space merges). What they cover, as tiers:

1. **Config** — the weight → lever mapping in isolation.
2. **Text** — Krea 2's real tokenizer behind the *real* `Qwen3VL4BEngine` and `SDClipModel`, with a stand-in transformer, so tokenisation, the template strip and the emphasis classes are Forge's own code. An unweighted prompt must come out bit-identical to the engine's own encode. On MOSS-Image the same with the extension's real `MossTextEngine`, `restore_layout_json` and `TEMPLATE`: an unweighted prompt and a layout prompt bit-identical to `engine.encode`, a claimed weight giving the unweighted sentence's conditioning with exactly the phrase's tokens flagged and the template's neutral, an unclaimed one giving `encode_token_weights`' lerp.
3. **Model** — a real (not mocked) tiny `nn.Module` shaped like `SingleStreamDiT`, asserting byte-level that exactly the intended rows of `wv` change and by exactly the expected factor, and that unpatching is a true inverse down to the instance dictionary. On MOSS-Image the extension's real `MossImageDiT` at a tiny size with Comfy-Org's fused q/k/v: the flagged token's row changes in the value third only, at its *trailing* position, image rows and q/k untouched; neutral rows reproduce the unpatched output exactly; the bias reaches `attention_pytorch` as a `(B, 1, image + text)` mask with the bias on the trailing text key in the selected blocks and over the text keys alone in the refiners, and the unselected blocks keep the original kernel; the negative-pass block skip gives the same output as unpatched; a 4-layer model is refused with `the DiT has 4 layers, not 42` until the shape constants are patched to match.
4. **Pipeline** — the real `prompt_parser` and `backend/sampling/condition.py` functions chained end to end, proving cond and uncond stay row-aligned once Forge's batching code has had them.
5. **Contract** — reads Forge's actual source files and asserts every precondition the port rests on: the attributes detection reads, the module names the hooks wrap, the forward signatures, the argument assumed to always be `None`, the tensor rank the conditioning arrives in, the template token ids. Tiers 1–4 test the extension against a *model* of the framework, and that model moves with our assumptions rather than Forge's — this is the only tier that fails when Forge changes rather than when we do. The MOSS-Image check is its own contract tier in effect: it imports the extension's real modules, so a rename there fails the check rather than the fakes.

The prompt parser is part of that contract, and it has already moved once. Until Forge Neo commit `c6b22915` (2026-09-24) there were two copies of `parse_prompt_attention`: one in `modules/prompt_parser.py`, one in `backend/text_processing/parsing.py`. The commit deleted the first, pointed `emphasis.py` at the second, and changed `uses_emphasis` so that a bare `BREAK` now counts as emphasis. The extension binds to the surviving copy, `parsing.parse_prompt_attention`, called with the emphasis name — its regex, its negative-weight capture and its `BREAK` sentinel were untouched — so nothing here changed. The `BREAK` change cannot reach the levers either: activation and the rows both go through `weighted_segments`, which neutralises the sentinel before any weight is read, and `uses_emphasis` is only consulted for the `Emphasis` infotext line, where following Forge is the point. If the parser moves again, `prompts.py` is the one import to re-point; the offline checks run Forge's real parser and real text engine, so they are what says whether the move was clean.

The text engine moved next. Forge Neo commit `21886f41` (2026-09-30) replaced `Qwen3VLTextProcessingEngine` with `Qwen3VL4BEngine`, a port of ComfyUI's encoder wrapper. Three things the extension used are gone: `process_tokens(tokens, multipliers)`, which applied the selected emphasis to the input embeddings before the transformer ran; the writable `emphasis` attribute, now a read-only property fixed at `EmphasisNone`; and `id_template`. The HF tokenizer now sits under an `SDTokenizer` wrapper, and the engine's `tokenize` no longer strips. Upstream Krea 2 now parses no weights at all: the whole prompt goes to the encoder as literal text, brackets included. `text.py` therefore reads Settings → *Emphasis* itself, builds the templated token streams with the HF tokenizer directly, and runs `SDClipModel.forward` with the emphasis step put back between `process_tokens` and the transformer (`_encode_tokens`). All-`1.0` multipliers skip that step, so an unweighted prompt is bit-identical to the engine's own encode, and an unclaimed weight gets the same `EmphasisOriginal` on the input embeddings that it got before. The DiT side did not change.

With the engine reading weights as literal text, the extension can no longer wait for a weight it claims before it acts: a batch it left alone would hand `(word:1.2)` to the encoder brackets and all. So `scan` reports any weight that is not `1.0`, and that is what activates it. A batch whose weights are all unclaimed patches only the text hook, with a config that uses neither lever, and the hook then returns a bare list of conditionings, the engine's own shape: no rows, no `compile_conditions` wrapper, no DiT hooks, and nothing for the DiT settings to act on. An unclaimed negative weight, which happens only at *Value strength* `0`, reaches emphasis as `1.0`, not `abs(weight)`, so `0` still means "negative weights do nothing".

The parser eats the whitespace around `BREAK`, so rejoining its segments for the one-pass encode read `hat BREAK a dog` as `hatBREAKa dog`. Wider activation sent more prompts down that path, so `weighted_segments` now puts the sentinel back as ` BREAK `, a spaced word with weight `1.0`. Krea 2 has no chunk boundary for it to mean, and the engine reads it as the literal word, so a weighted prompt with `BREAK` now encodes like the same prompt without weights.
